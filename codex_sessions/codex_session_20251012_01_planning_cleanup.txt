─ Worked for 7s ──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

• Switching Frontier’s internals to UTF‑8 would be a fundamental shift—arguably the biggest single modernization you could tackle. Today nearly every layer
  assumes “classic Mac” byte strings (Pascal bigstring, unsigned char handles with embedded type IDs, AppleScript descriptors, etc.), so the change impacts both
  architecture and observable behaviour. Here’s how I’d frame it:

  Where UTF‑8 touches the codebase

  - bigstring/Handle APIs (strings.c, memory.c, portable_handles.c, langvalue.c, langhash.c) expect byte counts that map 1:1 to characters. UTF‑8 blows that up
    (variable width, need to track code points vs. bytes).
  - The language runtime (parsers, scanners, langhash, langxml, op subsystems) manipulates text directly, slicing on byte offsets, assuming ASCII/extended
    MacRoman. Anything that does “character arithmetic” must be UTF‑8 aware or it will corrupt data mid‑codepoint.
  - DB serialization (tablepack, hashpack), UserTalk storage, AppleEvent descriptors, and headless stubs all encode/ decode today’s legacy encoding. Changing them
    means new on-disk formats or at least new conversion flows.
  - External integrations (CLI, portable runtime, OSA bridges) would need consistent UTF‑8 expectations to avoid double-conversion or mojibake; currently a lot of
    glue code is “just treat bytes as they are”.

  Large-scale implications

  - Database compatibility: existing .root files store Pascal strings + legacy encodings. A UTF‑8 runtime must still read legacy content, so you either keep the
    old representation and convert lazily, or define a migration step that rewrites string data in place (same scale as the 64‑bit migration).
  - Script compatibility: UserTalk scripts that poke at bytes (length, char(n), substring by byte index, etc.) would change behaviour once characters occupy
    multiple bytes. You’d want a very clear compatibility story (compat mode, warning pass, or a versioned dialect).
  - Performance + memory: UTF‑8 keeps memory footprint smaller than UTF‑16, but any operation that needs random access by character starts to cost (walk from
    beginning to find the Nth codepoint). You may have to add helper APIs (UTF‑8 aware indexing, normalization) to avoid O(n²) behaviour.
  - API surface: Callers that expect Pascal strings (\p) or MacRoman characters (e.g. the literal '\p==' all over the runtime) need replacements. This refactor
    would ripple through the entire codegen, not only the runtime.
  - Testing: Everything—from parser tests to file I/O and DB migrations—needs fresh cases with multi-byte characters (accented Latin, emoji, combining marks,
    right-to-left scripts). Without robust coverage the regressions will be brutal.

  Feasibility and sequencing ideas

  1. Char set boundary inventory: catalogue every place we convert between encodings (internal vs. disk vs. AppleEvent vs. CLI). Decide the canonical form (UTF‑8
     internally, maybe still Pascal/legacy on disk for backward compatibility) and document it first.
  2. UTF‑8 aware primitives: introduce UTF‑8 helper functions into strings.c (length in codepoints, forward/backward iteration, validation). Once those exist,
     gradually replace raw byte math.
  3. Layer-by-layer opt-in: e.g. start with portable CLI/ tests, then the language runtime, then DB pack/unpack. Provide compatibility functions that still expose
     Pascal strings to legacy callers so you don’t have to flip everything at once.
  4. DB strategy: either add a per-string “encoding” flag and lazily convert, or declare a new DB version that requires a migration (like the 64-bit structural
     modernisation). The latter is simpler but is a flag-day for everyone.
  5. Script-level impact plan: publish a draft spec—“UserTalk 2” or similar—listing breaking changes (string length counts codepoints, etc.), and maybe ship
     transition helpers (e.g. string.bytes() vs string.length()).
  6. Compatibility shim period: for a time, allow both legacy and UTF‑8 builds on the branch (e.g. compile-time flag) so plugin/extension developers can vet their
     code.

  Risks & mitigations

  - Silent data corruption if partial conversions mix (UTF‑8 inside, MacRoman outside). Mitigate via rigorous audit + conversion helper macros.
  - Performance regression due to repeated validation or scanning. Mitigate by caching lengths or normalizing once.
  - Migration blockers where third-party scripts rely on byte-level semantics. Mitigate with feature flag / compatibility switch, maybe tooling to scan scripts
    for problematic patterns.

  In short: worth considering, but it’s not “a phase” so much as “a multi-phase programme” with high coordination overhead. I’d only commit once we have the
  migration plan, compatibility strategy, and the appetite to break legacy behaviour (per your note about UserLand’s rule #1). If you’re ready for that, the to-do
  list above gives a rough playbook for scoping the work.

• Current String Model Snapshot

  - Data structures – most kernel APIs work with Pascal bigstring (#define bigstring Str255, Common/SystemHeaders/standard.h:211) and assume 8‑bit characters. The
    macros stringlength, lastchar, etc. operate on raw bytes (Common/SystemHeaders/standard.h:283-303). Longer strings live in Handles whose content is treated the
    same way (Common/headers/memory.h:75-226, Common/source/langvalue.c:600-655).
  - Lower/upper casing – a 256‑entry lookup table drives case conversion (Common/headers/strings.h:42, Common/source/strings.c:2567-2570); uppertext/lowertext
    simply walk bytes (Common/source/strings.c:1417-1446).
  - Parser/runtime – tokenisation and identifier checks rely on isalpha/isdigit working on single bytes (Common/source/langscan.c:44-115). In effect, every language
    feature—from string.nthWord to path handling—assumes one byte per character.
  - Encoding helpers – strings.c still depends on Carbon’s Text Encoding Converter (TEC) for all conversions (Common/source/strings.c:2269-2338, 2367-2559).
    Convenience verbs expose ANSI ⇄ UTF‑8 and MacRoman ⇄ UTF‑8 transforms (Common/source/stringverbs.c:2250-2278).

  Platform-Specific Assumptions

  - macOS UI/FS code injects or expects MacRoman: Nav Services prompts (Common/source/filedialog.c:312-337), FS path utilities (Common/source/filepath.c:96),
    machine name fetching (Common/source/fileops.m:173, 2198, 2893), time/date formatting (Common/source/timedate.c:256-466).
  - Windows code paths target Windows Latin‑1 (Common/source/strings.c:2367-2449) and registry verbs rely on the same byte semantics (Common/headers/
    winregistry.h:111-137).
  - Headless stubs fake classic constants (Common/headers/headless_stubs.h:114-118), meaning conversions silently no-op unless we provide real tables.
  - langstartup.c enumerates legacy encodings through GetTextEncodingName (Classic APIs, Common/source/langstartup.c:507-510).
  - AppleEvent plumbing (Common/source/langsystypes.c, e.g. 1454-1466, 1886-1894) serializes Pascal strings without Unicode awareness.

  Script-Level Surface

  - UserTalk exposes MacRoman ↔ UTF‑8 verbs (string.macRomanToUtf8, string.utf8ToMacRoman, Common/source/stringverbs.c:2250-2278) in addition to ANSI helpers. Most
    other string.* verbs (split/truncate/upper) operate on byte offsets, so multi-byte UTF‑8 would change semantics unless we add codepoint-aware variants.
  - Because the runtime uses isalpha/tolower, behaviour already varies with locale; on macOS the default “C” locale roughly matches MacRoman. Moving to UTF‑8
    without revisiting these would create surprising results for scripts expecting byte-oriented behaviour.

  UTF‑8 Migration Plan (High Level)

  1. Inventory & Spec
      - Map every kernel API that produces/consumes text (handles, Pascal buffers, CF/Win32 bridges). Use references above plus: Common/source/langhash.c string
        packing, Common/source/langxml.c:2470-2497, Common/source/op* outline text paths, database pack/unpack (Common/source/tablepack.c:320-343, Common/source/
        langhash.c:1952-2074).
      - Document current encodings on disk (packed tables store raw byte handles) and over the wire (AppleEvents, TCP/XML utilities). Decide new canonical internal
        encoding (UTF‑8) and compatibility expectations.
  2. Lay Foundations
      - Introduce a UTF‑8 utility layer (validate, decode/encode code points, iterate, case mapping). Replace global tables (lowercasetable, isfirstidentifierchar)
        with helpers that can grow beyond 256 values. Consider ICU/CoreFoundation (CFString/CFStringTransform) or a lightweight embedded library.
      - Add explicit APIs for byte length vs. character length (string_bytes, string_chars) so we can update call sites incrementally.
  3. Core Runtime Conversion
      - Update strings.c, memory.c, and langvalue.c to treat string handles as UTF‑8. textfindreplace, langcommentdelete, word/field utilities, and langscan must
        move from byte indexing to codepoint-aware traversal.
      - Replace TEC usage with modern APIs (CFString on macOS; ICU or Win32 MultiByte conversions elsewhere) and ensure headless builds provide an equivalent
        (likely an embedded UTF‑8 library).
  4. Persistence & IPC
      - Define a database migration strategy. Options:
          - Lazy conversion: keep existing byte blobs, mark encoding, convert when a value is touched (requires flags in tyvaluerecord and tablepack updates).
          - Versioned migration: add a new DB format version, upgrade all text records to UTF‑8 in place (similar to the 64-bit v7 bump). Requires tooling and
            backup plan.
      - Update AppleEvent bridges (langipc, langsystypes), XML/HTTP utilities, and any CFString bridges to pass UTF‑8 cleanly.
      - Ensure headless stubs either reuse the new helpers or explicitly stub as UTF‑8 to stay in sync.
  5. UserTalk Surface & Compatibility
      - Decide how existing verbs behave. Options:
          - Maintain byte-oriented semantics for backward compatibility and add stringUtf8.* equivalents, or
          - Retain names but change semantics, guarded by a compatibility toggle (e.g., system preference or script metadata).
      - Keep MacRoman/ANSI conversion verbs as compatibility shims but reimplement on top of new helpers.
      - Update documentation to signal the behavioural changes and provide migration guidance for scripts that index by byte.
  6. Testing & Tooling
      - Expand unit/integration tests (e.g., tests/runtime_tests, tests/string_*) with multi-byte inputs (accented Latin, emoji, combining marks, RTL scripts).
      - Add validation for DB roundtrip, AppleEvent exchanges, HTTP/XML exports.
      - Provide optional script analyzer to flag byte-based assumptions (e.g., charPos, mid, setcharvalue with high ASCII).
  7. Rollout
      - Stage behind a feature flag or dedicated branch until parity reached.
      - Offer migration utilities (database upgrader, script linter).
      - Communicate breaking changes (Rule #1 exception) and gather feedback before defaulting to UTF‑8.

  Kernel Hotspots Requiring Extra Attention

  - Common/source/strings.c – all core helpers; converttextencoding currently uses TEC (Carbon-only), BOM stripping at lines 2296-2314 must survive.
  - Common/source/stringverbs.c – expose new UTF‑8 aware verbs; existing MacRoman helpers become compatibility wrappers.
  - Common/source/langscan.c / langparser.c – scanner/tokenizer uses 8-bit tables; rewrite needed to avoid corrupting multi-byte tokens.
  - Common/source/langhash.c / tablepack.c – binary packing/unpacking writes raw bytes; must embed encoding metadata or convert during migration.
  - Common/source/langxml.c:2470-2476 – XML attribute serialization copies percentages with insertchar. Needs UTF‑8 aware quoting/escaping.
  - UI/FS bridges (filedialog.c, filepath.c, fileops.m, timedate.c, langstartup.c) – replace MacRoman constants with UTF‑8/CFString conversions and ensure Windows
    equivalents use UTF‑16 or UTF‑8.
  - AppleEvent/OSA layers (langsystypes.c, langipc.c, osacomponent.c) – currently build Pascal strings and rely on legacy encodings; must switch to Unicode
    descriptors (typeUTF8Text or typeUnicodeText).
  - Headless/test shims (tests/headless_mac_compat.c:427-460, tests/headless_lang_runtime_more_stubs.c) – align with new APIs to keep tests meaningful.

  Risks & Mitigations

  - Silent data corruption if some subsystems remain byte-based – mitigate with exhaustive audit and temporary asserts validating UTF‑8 inputs.
  - Performance regressions from repeated UTF‑8 scans – introduce cached metadata (e.g., store codepoint count alongside handles) for hot paths (outline rendering,
    parser).
  - Third-party script breakage – provide transitional compatibility mode and migration docs/tools.
  - Dependency drift – replacing TEC with ICU/CoreFoundation must account for headless builds; consider bundling a cross-platform UTF‑8 lib.

────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────

• Switching Frontier’s internals to UTF‑8 would be a fundamental shift—arguably the biggest single modernization you could tackle. Today nearly every layer
  assumes “classic Mac” byte strings (Pascal bigstring, unsigned char handles with embedded type IDs, AppleScript descriptors, etc.), so the change impacts both
  architecture and observable behaviour. Here’s how I’d frame it:

  Where UTF‑8 touches the codebase

  - bigstring/Handle APIs (strings.c, memory.c, portable_handles.c, langvalue.c, langhash.c) expect byte counts that map 1:1 to characters. UTF‑8 blows that up
    (variable width, need to track code points vs. bytes).
  - The language runtime (parsers, scanners, langhash, langxml, op subsystems) manipulates text directly, slicing on byte offsets, assuming ASCII/extended MacRoman.
    Anything that does “character arithmetic” must be UTF‑8 aware or it will corrupt data mid‑codepoint.
  - DB serialization (tablepack, hashpack), UserTalk storage, AppleEvent descriptors, and headless stubs all encode/ decode today’s legacy encoding. Changing them
    means new on-disk formats or at least new conversion flows.
  - External integrations (CLI, portable runtime, OSA bridges) would need consistent UTF‑8 expectations to avoid double-conversion or mojibake; currently a lot of
    glue code is “just treat bytes as they are”.

  Large-scale implications

  - Database compatibility: existing .root files store Pascal strings + legacy encodings. A UTF‑8 runtime must still read legacy content, so you either keep the old
    representation and convert lazily, or define a migration step that rewrites string data in place (same scale as the 64‑bit migration).
  - Script compatibility: UserTalk scripts that poke at bytes (length, char(n), substring by byte index, etc.) would change behaviour once characters occupy
    multiple bytes. You’d want a very clear compatibility story (compat mode, warning pass, or a versioned dialect).
  - Performance + memory: UTF‑8 keeps memory footprint smaller than UTF‑16, but any operation that needs random access by character starts to cost (walk from
    beginning to find the Nth codepoint). You may have to add helper APIs (UTF‑8 aware indexing, normalization) to avoid O(n²) behaviour.
  - API surface: Callers that expect Pascal strings (\p) or MacRoman characters (e.g. the literal '\p==' all over the runtime) need replacements. This refactor
    would ripple through the entire codegen, not only the runtime.
  - Testing: Everything—from parser tests to file I/O and DB migrations—needs fresh cases with multi-byte characters (accented Latin, emoji, combining marks, right-
    to-left scripts). Without robust coverage the regressions will be brutal.

  Feasibility and sequencing ideas

  1. Char set boundary inventory: catalogue every place we convert between encodings (internal vs. disk vs. AppleEvent vs. CLI). Decide the canonical form (UTF‑8
     internally, maybe still Pascal/legacy on disk for backward compatibility) and document it first.
  2. UTF‑8 aware primitives: introduce UTF‑8 helper functions into strings.c (length in codepoints, forward/backward iteration, validation). Once those exist,
     gradually replace raw byte math.
  3. Layer-by-layer opt-in: e.g. start with portable CLI/ tests, then the language runtime, then DB pack/unpack. Provide compatibility functions that still expose
     Pascal strings to legacy callers so you don’t have to flip everything at once.
  4. DB strategy: either add a per-string “encoding” flag and lazily convert, or declare a new DB version that requires a migration (like the 64-bit structural
     modernisation). The latter is simpler but is a flag-day for everyone.
  5. Script-level impact plan: publish a draft spec—“UserTalk 2” or similar—listing breaking changes (string length counts codepoints, etc.), and maybe ship
     transition helpers (e.g. string.bytes() vs string.length()).
  6. Compatibility shim period: for a time, allow both legacy and UTF‑8 builds on the branch (e.g. compile-time flag) so plugin/extension developers can vet their
     code.

  Risks & mitigations

  - Silent data corruption if partial conversions mix (UTF‑8 inside, MacRoman outside). Mitigate via rigorous audit + conversion helper macros.
  - Performance regression due to repeated validation or scanning. Mitigate by caching lengths or normalizing once.
  - Migration blockers where third-party scripts rely on byte-level semantics. Mitigate with feature flag / compatibility switch, maybe tooling to scan scripts for
    problematic patterns.

  In short: worth considering, but it’s not “a phase” so much as “a multi-phase programme” with high coordination overhead. I’d only commit once we have the
  migration plan, compatibility strategy, and the appetite to break legacy behaviour (per your note about UserLand’s rule #1). If you’re ready for that, the to-do
  list above gives a rough playbook for scoping the work.
