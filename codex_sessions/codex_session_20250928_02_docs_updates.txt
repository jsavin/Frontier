> Bottom Line

  - Stubbing and #if FRONTIER_HEADLESS is a good bridge for unblocking headless builds and tests, but it will not scale as a long‑term strategy. Plan a next phase that fully separates UI code
  behind explicit interfaces (ports/adapters). MVC/MVVM can be applied inside each UI implementation, but the core should be UI‑agnostic.

  What I See In Repo

  - Extensive headless gating and stubs across core files, e.g. Common/source/ops.c:31, Common/source/opedit.c:28, Common/source/langsystem7.c:30, Common/headers/file.h:38, and a very large
  AppleEvent/Carbon stub surface in Common/headers/headless_stubs.h:1.
  - Direct UI types leak into headers used by core: Common/headers/op.h:464 exposes WindowPtr outlinewindow; Common/headers/cancooninternal.h:117 uses WindowPtr, making consumers UI‑aware.
  - Mac toolbox umbrella headers still present: Common/headers/xMacHeaders.c:71 includes AppleEvents.h, Dialogs.h, Windows.h, etc.
  - The “headless” CLI links UI frameworks, suggesting coupling in the link graph: frontier-cli/Makefile:7 links AppKit and Carbon.

  Why This Won’t Scale

  - Surface area growth: Every new UI touchpoint requires more stubs and #if branches, increasing risk of divergence and bugs.
  - Header coupling: UI symbols/types in shared headers force UI dependencies into core or proliferate conditional blocks.
  - Test blind spots: Headless path behaves differently than UI path (duplicate implementations like numeric formatting in Common/source/ops.c:303 vs the non‑headless branch).
  - Build and portability drag: Even headless targets may need to link UI frameworks, complicating CI and cross‑platform work.

  Recommended Direction

  - Adopt a ports-and-adapters boundary for UI concerns:
      - Define narrow interfaces for UI‑facing services: Windowing, Menus, Dialogs, Clipboard, Text Rendering, Event Loop, Automation/AppleEvents.
      - Provide implementations per environment: Headless (no‑op/logging) and platform adapters (AppKit/Win32/etc).
      - Keep the core runtime depending only on these interfaces, never on platform headers or WindowPtr.
  - Internally, the platform UIs can use MVC on AppKit or MVVM on SwiftUI; Windows could use MVP. The core should not know which.

  Concrete Steps (Incremental, Low-Risk)

  - Create a UIServices vtable (function pointers) and a single “runtime context” that the core uses to request UI work.
      - Start by lifting the most common calls: message/log display, timers/backgrounding, file dialogs, clipboard, basic menu enabling.
  - Fence the core:
      - Introduce a FRONTIER_CORE or similar define for core targets; fail build if any platform UI header appears when this is set.
      - Move UI typedefs out of shared headers (e.g., replace WindowPtr in Common/headers/op.h:464 and Common/headers/cancooninternal.h:117 with opaque IDs or keep them entirely in UI
  modules).
  - Split targets:
      - Build libfrontier_core with no AppKit/Carbon/Win32 link flags.
      - Build frontier-cli against libfrontier_core only; remove UI frameworks from frontier-cli/Makefile:7.
      - Build platform apps that link both libfrontier_core and their UI adapter.
  - Replace conditional compilation with dependency inversion:
      - Migrate #if FRONTIER_HEADLESS blocks inside core to calls into UIServices and implement the divergence in the adapters.
      - Keep #if use localized inside adapters and stubs, not scattered across core.

  When To Switch From Stubs To Interfaces

  - You’re seeing new features require multiple new stubs/#if branches.
  - Headless build still pulls in UI frameworks or types.
  - Bugs diverge between headless and UI paths due to duplicate logic.
  - It’s difficult to add a non‑desktop UI (e.g., web) without touching core.

  Enforcement Tactics

  - Header hygiene: create core_includes.h without xMacHeaders; compile core with -Werror and a static assert or include guard that forbids UI headers.
  - Link hygiene: CI builds libfrontier_core with -Wl,--no-undefined (or platform equivalent) to catch leaked UI symbols.
  - Audit and track UI touchpoints: start with files flagged above and progressively move them behind the interface.

  MVC vs. MVVM vs. Hexagonal

  - MVC/MVVM are UI‑internal patterns. They won’t on their own decouple the runtime from UI frameworks.
  - Use hexagonal/ports‑and‑adapters to isolate the core. Then, pick MVC for AppKit or MVVM for SwiftUI inside the adapter. This gives you headless, native UIs, and a future web UI without
  core changes.

  Suggested Pilot Scope

  - Define UIServices with 6–10 functions required for headless CLI parity: logging/status, timers/backgrounding, clipboard, file open/save dialogs, menu enable/disable, alert/prompt.
  - Implement a headless adapter and swap a few #if FRONTIER_HEADLESS sites to interface calls.
  - Remove AppKit/Carbon from the CLI link and ensure frontier-cli still runs tests.
