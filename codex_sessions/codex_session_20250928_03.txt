> The “constants” table is a system table the language initializes at startup that maps well‑known identifier names to literal values. The compiler/scanner consults this table so that when you write those names in
  UserTalk, they behave like real literals instead of variables.

  What it contains

  - Nil and booleans
      - nil → novaluetype “no value”
      - true/false → boolean values
  - Numeric/special values
      - infinity → a large sentinel (from longinfinity)
  - Directions (enumerations)
      - up, down, left, right, flatup, flatdown, nodirection, pageup, pagedown, pageleft, pageright → directionvaluetype values
  - Type constants (by value type)
      - For each tyvaluetype (except those explicitly excluded like externalvaluetype, oldstringvaluetype, etc.), a constant of the form “<Type>” that evaluates to that value type.
      - Special alias: shortType → intvaluetype
      - Examples conceptually: stringType, intType, longType, listType, recordType, etc.
  - Machine/OS strings
      - machinePPC, machine68K, machineX86
      - osMacOS, osMacCn (Carbon), osWin95, osWinNT

  Where it lives and how it’s used

  - Location: created as a system table under the language table: langtable["constants"].
  - Population: langinitconsttable() builds it early during language initialization.
  - Consumption: The scanner/compiler looks up identifiers in this table (comment in code: “converted to constants by the scanner”) and replaces them with the corresponding literal value during compilation, so scripts
  can write e.g. true, nil, pageup, or stringType directly.

> Short answer

  - There’s no downside to starting the long‑term approach now for safe string handling — we should add general helpers and steadily refactor call sites.
  - BIGSTRING is a Pascal‑style, length‑prefixed literal used throughout Frontier; it differs from C strings (null‑terminated). Longer term, we can migrate most code to UTF‑8 C strings and keep BIGSTRING only at
  legacy boundaries (tokenizer, on‑disk formats, old Mac APIs) until those are modernized.

  What BIGSTRING is

  - Frontier uses “Pascal strings” called bigstring: the first byte stores the length (0–255), followed by that many bytes of payload (no trailing NUL). This dates back to Classic Mac OS Toolbox and Carbon-era APIs.
  - BIGSTRING("...") is a macro for compile‑time Pascal literals: it produces a length + data sequence directly in the object code. For example: BIGSTRING("\x05hello") encodes length 5 and then “hello”. It’s used
  widely to avoid runtime conversion costs and to interact with APIs that expect bigstring.
  - C strings are NUL‑terminated (char*), length discovered by scanning to '\0'. They are easier to interoperate with modern libraries, encodings, and I/O.

  Why BIGSTRING persists

  - Many language/runtime APIs (scanner/tokenizer, hash table keys, resource loaders) accept bigstring or ptrstring (Pascal pointer).
  - On‑disk formats and saved scripts embed Pascal strings.
  - Old Mac API shims and internal utility routines operate on bigstrings.

  Recommended “long‑term” steps (and we can begin now)

  1. Add canonical helpers in strings.h/strings.c
      - bs_from_c(const char* c, bigstring out)
          - Wraps copyctopstring(c, out) but documents the approved conversion.
      - c_from_bs(const bigstring bs, char* out, size_t out_sz)
          - Wraps copyptocstring with bounds.
      - hashinsert_cstr(const char* name, const tyvaluerecord* v)
          - Convenience for common table inserts that currently cast literal C strings to ptrstring.
      - setstringvalue_c(const char* c, tyvaluerecord* v)
          - Wraps setstringvalue with a temporary bigstring.
  2. Provide “_c” variants for init-time adders (constants/keywords/builtins)
      - langaddnilconst_c(name), langaddlongconst_c(name,x), langaddbooleanconst_c(name,b), langadddirectionconst_c(name,d), langaddtypeconst_c(name,t)
      - Internally convert name using bs_from_c and forward to the existing bigstring-based functions.
  3. Policy and refactor
      - Never cast C string literals to ptrstring (no (ptrstring)"foo"). That’s what caused the SIGBUS (writing into read-only storage).
      - Accept only:
          - BIGSTRING("…") when a true Pascal literal makes sense (rare).
          - bigstrings created via bs_from_c.
          - “_c” wrappers where we are setting constants or inserting hash keys.
      - Update langstartup.c and similar init code to rely on the “_c” helpers.
      - Sweep and replace high‑risk sites (constants, keywords, builtins, lang tables) first, then expand.
  4. Migration off BIGSTRING (medium‑term)
      - Start converting internal APIs that pass bigstring for internal operations to use const char* + size; keep shims for compatibility.
      - For on‑disk/network formats that encode Pascal strings, keep conversion at I/O boundaries only.
      - Tokenizer/scanner: eventually accept C strings directly and retire heavy use of Pascal API.

  Why not go all‑in immediately?

  - Going wide (replace across the runtime) risks destabilizing large areas while we’re still bringing tests online. But there’s no reason not to start by adding general helpers and refactoring central init code now —
  it’s low risk and reduces repeated fixes.
  - We can take an iterative approach: add the helpers, refactor the language initialization and other early modules, keep BIGSTRING where it’s still needed, and expand refactors as tests mature.

  Offer

  - I can add bs_from_c, c_from_bs, and the generic “_c” wrappers to strings.{h,c} and refactor langstartup.c to use them (cleaning up the ad‑hoc wrappers just added). We’ll use these helpers going forward so we don’t
  repeat the pointer‑to‑literal problems.
  - We can also add a grep guard in the plan (or a lint step later) to flag (ptrstring)" usage.

  Bottom line

  - Let’s put the general helpers into the core strings module now and start refactoring high‑risk call sites (constants/keywords/builtins init) to use them. BIGSTRING can stay for now at legacy boundaries, but over
  time, we’ll pivot most internals to C strings.
