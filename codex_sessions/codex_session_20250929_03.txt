      - Levels: off/1/2/3 (INFO/DEBUG-like)
      - Targets: file/about/dialog/debugger
  - It is compile‑time gated, which is common for C projects wanting zero cost when disabled.

▌ langparser.y is a huge file. Is there a sensible way to split it into logical pieces?

> Yes. Given Bison 2.3 and the single “%%” constraint, the most practical and low‑risk approach is to keep a generated monolithic langparser.y but compose it from smaller, logically grouped fragments.

  Recommended structure

  - Prologue (C code)
      - File: prologue.ypp
      - Contents: includes, typedefs, Bison shims (yylex/yyerror prototypes, pcyyerrct→yynerrs), YYSTYPE config, shared helpers.
  - Tokens & precedence
      - File: tokens.ypp
      - Contents: %token list, %left/%right precedence, %type declarations.
  - Grammar rules (split by concern)
      - File: rules_top.yg
          - module, statementlist, namelist, handler headers.
      - File: rules_stmt.yg
          - statements: if/while/for/case/bundle/try/handlers/assign/local/global.
      - File: rules_ref.yg
          - deref/dotted/array/range/function calls/identifier forms.
      - File: rules_expr.yg
          - expression hierarchy: unary/binary ops, literals, coercions.
  - Epilogue (C code)
      - File: epilogue.ypp
      - Contents: yytrace (debug), yylex wrapper, yyerror, small action helpers.

  How to stitch it together

  - Simple composer script (preferred with Bison 2.3):
      - scripts/compose_langparser.sh
      - Concatenates in this order:
          - prologue.ypp
          - tokens.ypp
          - “%%”
          - rules_top.yg + rules_stmt.yg + rules_ref.yg + rules_expr.yg
          - “%%”
          - epilogue.ypp
      - Then calls scripts/gen_langparser.sh (which runs bison and applies the small YYSTYPE post‑fix if needed).
  - Keep the generated langparser.y checked in (source of truth for build), but develop and review changes in the fragments. The composer is run only when fragments change.

  Why this approach

  - Compatible with Bison 2.3 (no native %include for grammar sections).
  - Keeps exactly one “%%” pair, avoiding parser structure pitfalls.
  - Logical boundaries make review and modernization (YYABORT/YYACCEPT, cleaner actions) tractable.
  - Doesn’t force immediate runtime change; you can continue to ship the legacy generated C until the Bison transition is complete.

  Additional cleanup that helps

  - Move bulky semantic action helpers into a separate C file (e.g., langparser_actions.c) and call them from actions; that shrinks the .y content without touching grammar.
  - Once we pin a newer Bison, we can evolve to use %code, %printer, %destructor, and (if available) %include to reduce the need for an external composer.

▌ I assume that Bison 2.3 is what ships with macOS and/or Xcode. Is there a good reason to upgrade/migrate to Bison 3? Are there good reasons not to? What's the tradeoff?

> Short answer: Upgrading to Bison 3.x is worthwhile for correctness, features, and maintainability. The main tradeoff is adding a toolchain dependency (for generation only). You can mitigate that by committing
  generated C and keeping local builds tool-agnostic.

  Why upgrade (Bison 3.x benefits)

  - Safer skeletons: Modern error paths and stacks; avoids legacy UB patterns like statestack[-1].
  - Cleaner APIs:
      - %define api.value.type {hdltreenode} instead of ad-hoc macros
      - %parse-param/%lex-param for passing context/state
      - Reentrant parsers (%define api.pure full) if needed later
  - Error handling:
      - %destructor for automatic cleanup of semantic values on errors
      - Better diagnostics and YYERROR_VERBOSE behavior
  - Extensibility:
      - %code blocks (top/req/provides) to keep C glue clean
      - %printer for nicer debug traces
  - Ecosystem: Bison 3.x is current and actively maintained; more docs, examples, fixes

  Reasons to stay on 2.3 (or not upgrade everywhere)

  - Zero new dependency: macOS/Xcode often ship 2.3; no Homebrew/MacPorts prereqs for devs.
  - Minimal churn: Legacy MacYACC-style grammar compiles as-is; fewer changes needed short term.
  - Predictable behavior: Sticking with the tool Apple ships avoids version drift on contributor machines.

  Tradeoffs and practical approach

  - Developer experience vs. durability:
      - 2.3 keeps contributors tool-less, but you keep fighting legacy skeleton quirks and lack newer features.
      - 3.x unlocks cleaner grammar, better error handling, and long-term safety.
  - The middle path (recommended):
      - Use Bison 3.x to generate langparser.c in CI or a “prepared” environment.
      - Commit the generated C (and header if needed) to the repo.
      - Keep local builds using the committed generated files — no bison requirement for contributors.
      - Keep our compose/regenerate scripts tolerant of 2.3, but prefer 3.x when available.

  Impact on this codebase

  - Current issue: the project reads yyval outside yyparse. In C, yyval isn’t a global in modern skeletons. We’re already addressing this with a dedicated result (langparser_result). That change makes the grammar more
  portable to 3.x.
  - Cleanup opportunity: with 3.x we can replace goto/return action flows with YYABORT/YYACCEPT and %destructor-driven cleanups. That reduces custom stack manipulation and makes the parser more robust.

  Risks/caveats

  - Regeneration differences:
      - Generated code structure changes (no global yyval, local variables, API behavior).
      - Token/type header content may differ; keep a stable langparser.h or adapt generated defines carefully.
  - Tooling on macOS:
      - System /usr/bin/bison may be 2.3. Installing 3.x via Homebrew places bison at /opt/homebrew/opt/bison/bin/bison (not on the default PATH). Your scripts should handle this (use a BISON env var or discover it).
  - License: Bison’s special exception still applies; generated code can be used under the project’s license.

  Recommendation

  - Adopt Bison 3.x for regeneration only; keep generated sources in the repo so devs aren’t blocked.
  - Continue the grammar refactor (replace legacy gotos/returns with YYABORT/YYACCEPT, add result handle).
  - Once runtime tests pass with regenerated C, pin the Bison version in docs/scripts and CI, and keep 2.3 compatibility in the composer/regeneration path if feasible.

      - Gate 3.x-only features with conditional grammar blocks, falling back to 2.3-friendly code where needed.
      - Finish the conversion and present a status diff + test output before any PR.

> Here’s a quick, candid take on deeper cleanup, plus coverage realities.

  Plusses

  - Consistent semantics: Replacing legacy returns/gotos with YYABORT/YYACCEPT everywhere makes error paths predictable and easier to reason about.
  - Easier upgrades: A fully Bison-style grammar (no legacy stack pokes) simplifies moving to Bison 3 and adopting %destructor/%printer later.
  - Better diagnostics: Cleaner action flow and top-level acceptance yield clearer, less fragile error reporting.
  - Lower future risk: Less chance of obscure reductions “succeeding” with half-baked nodes; fewer parser-only footguns.

  Minuses

  - Churn risk: Touching complex rules (handlers, control flow) can cause subtle regressions if a reduction or precedence nuance differs.
  - Time cost: It’s painstaking; converting, regenerating, and validating iteratively takes focused effort.
  - Short-term limited payoff: If those constructs aren’t yet used in headless paths/tests, benefits are deferred until more features are exercised.

  Current test coverage

  - Covered: simple expressions (3+4), constants, and OPML round-trip paths — these validate expr/term chains and a slice of module handling.
  - Gaps (not covered by runtime_tests):
      - Handlers and headers: ontoken/bracketedidentifier/parameter lists; handler bodies.
      - Control flow: if/then/else; while/for/to/downto; case; continue/break; with; try/bundle.
      - Declarations: local/global; namelist variants; optional initializers.
      - Kernel calls: kerneltoken dottedid() cases.
      - Error recovery: malformed inputs (missing tokens, unmatched parens/braces), verifying yyerror flow.

  Recommendation

  - Proceed, but pair cleanup with targeted tests so we don’t regress:
      - Add parser/evaluator miniscripts to runtime_tests (or a new parser_tests.c):
          - Assignments: term := expr
          - if/then/else: local(x=1); if x==1 then 2 else 3
          - while/for: while false do 0 (no-ops), for i=1 to 3 { i } (ensure it parses/executed)
          - case: case x of { 1: 'a'; 2: 'b' } (if supported)
          - handlers: on foo(x) { x + 1 } (parses into a tree)
          - local/global blocks and semicolon/comma list variants
          - kernel call: kernel.something()
          - Negative tests: unmatched ), missing then, dangling comma, etc., to confirm YYABORT paths.
      - Keep PARSER_TRACE available (guarded) to diagnose any failures quickly.

  Tradeoff call

  - If you want minimal risk and fast progress: convert the remaining simple/medium rules (declarations, straightforward control flow) with a thin layer of tests and stop before the trickiest constructs.
  - If you want to “finish the job”: convert the full grammar and invest in a parser test suite. Time is higher, but you’ll bank robustness ahead of Bison 3 and future features.
