    # Portable Handle Runtime

    This module re-implements classic Mac OS "Handle" behaviour in pure C so the
    Frontier runtime can allocate movable blocks on platforms that no longer expose
    Toolbox memory APIs.  It mirrors the semantics relied on throughout the core:

    * Handles are stable pointers to pointers. The data buffer may move when
      resized, but the handle value itself never changes.
    * `HLock`/`HUnlock` bump a lock count so callers can assert correct pairs while
      receiving the raw data pointer.
    * Resizing preserves existing contents and zero-fills any newly allocated tail
      bytes to match historical expectations.

    The implementation lives in `Common/source/portable_handles.c` with public
    prototypes in `Common/headers/portable_handles.h`.  Platforms that do not ship
    Carbon headers automatically enable the portable layer via
    `FRONTIER_USE_PORTABLE_HANDLES` (set in `frontierdefs.h`).  Projects targeting
    other environments may opt-in explicitly by defining the same macro on their
    compiler command line.

    ## Integration notes

    * Existing code continues to call `NewHandle`, `DisposeHandle`, etc. through
      `macconv.h`. When the portable flag is active, those macros now map directly
      onto the new runtime.
    * The Windows implementation in `Common/stubs/megastubs.c` is left untouched; it
      continues to provide the classic behaviour on that platform.  The portable
      layer covers macOS (when Carbon is unavailable) and POSIX targets such as
      Linux.
    * `TempNewHandle`/`TempDisposeHandle` are backed by the same allocator. They set
      `memFullErr` on failure to preserve existing error handling logic.

    ## Next steps

    * Audit the call sites that rely on Carbon headers and move them behind the same
      portability guards so the core can be built on Linux without pulling in
      deprecated Apple frameworks.
    * Add focussed unit tests that exercise the handle manager (allocation,
      resizing, lock counting) once the cross-platform build harness is in place.

▌ I want to digress for a minute on some UI-related discussion. Froniter was ported from Classic MacOS to Windows in 1995 and 1996, with the windows
▌ version launching in early 1997, and used for most production deployment from that point on. There were four of us doing development work, one mostly
▌ in the C code, and the other three almost entirely in UserTalk code -- two of us using MacOS for development and one using Windows during that
▌ timeframe. What I'm wondering now is how the very Mac-centric UI code was made to work on Windows, and are there patterns that we can follow there in
▌ order to make a bare-minimum modern UI to work with. In the long run my plan for the product is to have the core runtime run headless in its own
▌ process, and to build a UI as a separate application that runs in its own process. Ideally the UI should be able to connect to a runtime instance
▌ over TCP/IP so that one can manage servers remotely using the UI application. (Think a little bit like Plex Media Server, and their collection of
▌ client applications that connect via a REST API.) But right now there might be lessons to learn from the Windows port that will help unblock some of
▌ the modernization we're doing right now.

> The old Windows port actually gave us a lot of the abstraction work we need for a modern, headless‑plus‑UI architecture.

  What the 1996/97 port did

  - The C core that we’re working on today is already shared between platforms: the Mac “shell” code lives under Common/source/shell*.c, and Windows
  equivalents sit alongside it in Common/source/frontierwindows.c, Winland.*, langdll.c, etc. The macconv header layer (see Common/headers/macconv.h)
  was created during that port to hide the classic Mac toolbox APIs behind cross‑platform macros. On Windows those macros are mapped onto Win32
  (frontierAlloc, frontierLock, etc.), while on Mac they still point to QuickDraw/Carbon.
  - The UI code didn’t get rewritten from scratch; instead, Windows built a parallel set of thin wrappers that satisfied the same interface the runtime
  expected. The bulk of the runtime, database, and verb engine stayed untouched, which is why we can still compile it all today.

  How we can reuse those patterns

  - Treat the current shell layer as the replaceable part. The runtime (everything under Common/source/lang*.c, db.c, etc.) already operates headless
  when the right callbacks are in place. We can lift the same separation for a modern UI by putting a thin adapter in front of the runtime.
  - For a minimal UI (whether native or web), follow the Windows pattern: expose a small set of “shell” entry points (open window, render outline,
  respond to menu commands) and implement them in whatever toolkit makes sense. The existing shell functions give us the blueprint for what the runtime
  expects.
  - For a headless/server mode, we can simply not load any shell implementation. The runtime already uses langcallbacks and similar structures to talk
  back to the UI; we can wire those to no-ops or to a network bridge instead.

  Toward the Plex-style architecture

  - We can stand up the headless core as a long‑running process that exposes a TCP API. Frontier already has networking and IPC layers (Common/source/
  langipc.c, langipcmenus.c); once the runtime is clean we can adapt those to a REST/gRPC interface.
  - Separate UI clients can then connect over that API. The Windows port proves that the UI doesn’t have to be in-process—just that it needs to drive
  the same verbs and callbacks.

  Bottom line

  We don’t need to refactor the UI to get the runtime tests going. The Windows port isolated the “shell” sufficiently that we can reuse the same
  boundaries today: keep the shell out of the headless harness, and eventually replace it with a modern client that talks over the network. As we
  modernize, we can mine macconv.h, frontierwindows.c, and the other Win32 shims for the patterns that allowed the runtime to remain portable.
