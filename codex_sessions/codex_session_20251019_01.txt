• Short version: the legacy kernel brings system.verbs online long before any UI layer is involved, but our sanitized root simply doesn’t include those tables. The
  old loader:

  - ccloadfile() → ccloadsystemtable() → tableloadsystemtable() pulls the root symbol table from the DB, then settablestructureglobals() walks system, system.verbs,
    system.verbs.builtins etc. via checktable(). When those subtables exist they’re marked as system tables; no UI required.
  - After the globals are set, linksystemtablestructure() wires in internaltable, environment and other runtime-plumbed tables; finally loadsystemscripts()
    runs system.startup and system.agents, compiling handlers as needed. All glue scripts (e.g. system.verbs.builtins.file.open, system.verbs.globals.new,
    system.verbs.builtins.launch.anything) reside in system.verbs inside Frontier.root itself.

  Because our sanitized headless root lacks system.verbs (and even the script table), checktablestructure() creates empty stubs, so dotted lookups fall back to the
  headless EFP shim and you see the langexternalgettable misses/segfaults. Exporting glue to text isn’t how the legacy system bootstraps; there’s no C compilation of
  those scripts—they live in the database and are interpreted once the root tables load.

  Next steps depend on how you want the headless runtime to honor that contract:

  - Option 1: ship a “real” root – reintroduce a minimally sanitized Frontier.root that still includes system.verbs (and related tables). Once those tables load, the
    CLI can resolve system.verbs.* immediately.
  - Option 2: code-generate a minimal system.verbs snapshot – use the old export pipeline to generate C that registers the glue tables at startup until we can rely on
    an augmented root. That keeps the semantics: system.verbs -> kernel -> EFP.
  - Either way, update the CLI hydration to ensure those tables are in place before tests try to reach them.

  Until one of those is in place, headless tests can’t assert anything about system.verbs. The right fix isn’t tweaking the CLI but deciding how to deliver those
  tables (real DB vs generated bootstrap). Let me know which route you prefer and we can start implementing it.
