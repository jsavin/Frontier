Suites

A suite is a collection of scripts of common purpose. Suites usually, but not always, have their own menu.

You can think of a suite as an application that runs inside Frontier.

Using a suite

To use a suite, go to the Main menu's Suites submenu and choose the suite's name. You should see a new menu with the name of the suite. The top entry of the menu might be named Read Me, About This Suite, or something similar. Selecting it opens the documentation for this suite. Follow the instructions regarding the purpose of this suite and how to use it.

When you're finished using a suite, you can remove its menu from the menubar by choosing Minimal Menus from the Suites menu. You can always use the suite again later.

Importing a suite

Suites are imported by double clicking on the file or selecting Open from the File menu and navigating to the file and opening it.

Suites may also appear in a fat web page: to get the suite from the page, save the source of the web page to disk, then open the source by selecting Open from the File menu.

Five elements are common to most suites

  1. They are stored in the root.suites table.

  2. They have a script called "init."

  3. They have a menu.

  4. They have a "readMe" explanatory document.

  5. They have a "suiteName."

Rules of the Road for suites developers

To create a new suite, go to Main menu -> Suites->New Suite.

When the dialog box appears, type the name of your suite. Frontier will create a new table for your suite and include the elements mentioned above.

"Init" is short for initilization. Any preparation required for your suite -- the creation of tables, default preferences, structures, etc. -- should be part of this script. A best practice is to call the init script from any starting point in your suite, thus ensuring that all the "support mechanisms" are in place, regardless of where a user begins.

An important convention is that no user data is stored in a suite table. You'll note that the default init script creates a table in the user table with the name of your suite. This table is where user data should reside. Data residing in a suite table will get overwritten with each bug fix or update -- an obviously frustrating experience for your users.

Another convention is not to clutter someone's root with needless persistence of one time data. If what you are working with is not too memory- or processor-intensive, not storing this data at all would be best. You can use the system.temp table. This table empties itself on startup -- this is the place to implement caching and other forms of one-time data. You can avoid stepping on someone else's temp data by using a unique name, and in the case of multiple items create a table for your suite in the system.temp table.

The suiteName entry is used by the script that builds the Suites submenu at startup. That's why your newly created script isn't yet present in the Suites menu.

You can rebuild this menu by opening the Quick Script window and running menus.buildSuitesSubmenu ().

While you can have more than one menu for your suite, only one suite can have its menu in the menubar at one time.

Another suggested convention is to include a "version." This makes it easy for your users to keep track of revisions -- and easy for you, too. The version string should be formatted as to be readable by other scripts and by people. Standard formats such as "1.0.2" and "3.2b3" are recommended.
