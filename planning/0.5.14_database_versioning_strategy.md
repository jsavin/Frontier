## **Problem Statement**

The Frontier refactoring needs to introduce a new database format with 64-bit compatibility, improved hash tables, and modern features while maintaining backward compatibility with existing `.root` files.

## **Current Database Version System**

### **Version Numbers**
- **Current**: `dbversionnumber = 6` (with `SMART_DB_OPENING`)
- **Legacy**: `dbversionnumber = 5` (without shadow avail list caching)
- **Major Version Check**: `majorversion(v) = (v & 0x00f0)`
- **Minor Version Check**: `minorversion(v) = (v & 0x000f)`

### **Current Error Handling**
```c
if (majorversion ((**hdb).versionnumber) != majorversion (dbversionnumber)) {
    dberror (dbwrongversionerror);
    goto error;
}
```

### **Structure Size Validation**
```c
assert (sizeof (tydatabaserecord) == 88);  // Current 32-bit size
// Will need: assert (sizeof (tydatabaserecord) == 80);  // 64-bit size
```

## **Proposed Strategy: Keep .root Extension**

### **1. Version-Based Compatibility**

**New Version Numbers:**
- **Legacy Format**: `dbversionnumber = 6` (current)
- **New 64-bit Format**: `dbversionnumber = 7` (new major version)
- **Future Format**: `dbversionnumber = 8` (for additional features)

### **2. Automatic Format Detection**

**When Opening .root Files:**
1. **Read header** and check `versionnumber`
2. **If version 6 or lower**: Use legacy 32-bit format
3. **If version 7 or higher**: Use new 64-bit format
4. **If major version mismatch**: Show specific error message

### **3. Migration Strategy (Explicit, Safe)**

**Policy:** Save implies migration to v7.

- Headless/CLI: Save triggers header‑only migration (with backup) before writing.
- UI: On Save menu, show a one‑time confirmation when migrating a legacy DB; then proceed.

**Backup:** Timestamped sibling file `yourfile.root.YYYYMMDD_HHMMSS`.

**Migration Mechanics:**
- Header‑only migration: rewrite the on‑disk header in the v7 layout; payload is copied as‑is.
- Atomic replace: write to `*.tmp`, flush, then `rename` to original name.
- Post‑check: Re‑read header to confirm `versionnumber == 7`.

### **4. Legacy Version Error Handling**

**For Old Frontier Versions Encountering New Format:**
```c
// In dbopenfile() - add specific error for new format
if ((**hdb).versionnumber >= 7) {
    // Show specific error message
    shellerrormessage ("This database was created by a newer version of Frontier. Please upgrade to Frontier 10.0 or later to open this file.");
    goto error;
}
```

## **File Extension Strategy**

### **Keep .root Extension**
- **Advantage**: No code changes required in existing applications
- **Advantage**: Users don't need to update file associations
- **Advantage**: Backward compatibility maintained

### **Backup Extension: .rbk**
- **Rationale**: "Root Backup" - clear and descriptive
- **Alternative**: `.root.bak` or `.root.legacy`
- **Implementation**: Automatic creation during migration

### **Migration Process**
```
Original: MyDatabase.root
Backup:   MyDatabase.root.YYYYMMDD_HHMMSS
New:      MyDatabase.root (version 7 header layout)
```

## **Error Message Strategy**

### **For Legacy Frontier Opening New Format**
```
"This database was created by Frontier 10.0 or later and uses a new format that is not compatible with this version of Frontier. Please upgrade to Frontier 10.0 or later to open this file."
```

### **For New Frontier Opening Legacy Format**
```
"This database uses the legacy format. Saving will migrate it to the modern format (v7). A timestamped backup will be created."
```

## **Runtime & CLI Behavior**

### **Headless/Runtime**
- Opening legacy (v≤6) DBs selects the legacy read path. No automatic background rewrite.
- Save on legacy DBs implies migration; until the Save‑path migration is fully wired, saves on legacy DBs will fail fast (no write) to prevent stamping v7 onto v6 layout.

### **CLI**
- `--auto-migrate`: Perform a header‑only migration with backup before operations when legacy is detected.
- `--dry-run` (future): Print analysis (version, headerLength, size delta) without writing.
- Non‑interactive by default; errors on read‑only or unwritable paths.

### **For Migration Confirmation**

```
The original file will be backed up as .rbk

```
