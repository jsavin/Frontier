# Phase 0.5.13: UserTalk Language Summary

## Summary

Based on exploration of the UserTalk documentation at `docs/usertalk/docserver.userland.com/` and the official "The UserTalk Language.pdf", this document provides a comprehensive overview of the UserTalk language, its structure, and its relationship to Frontier's database system.

## UserTalk Language Overview

### **What is UserTalk?**
- **Scripting Language**: UserTalk is Frontier's native scripting language
- **Object-Oriented**: Built around Frontier's object database system
- **Hybrid Architecture**: ~50% UserTalk scripts, ~50% C kernel implementations
- **Table-Based**: Verbs are organized in tables within the database hierarchy
- **Database-Centric**: Deeply integrated with Frontier's .root database files
- **Dynamic Typing**: Variables have no type until assigned, with automatic runtime conversion
- **Cross-Platform**: Supports both Macintosh and Windows environments

### **Language Architecture**

#### **1. Verb Implementation**
```
system.verbs.builtins.db.open  // Full path to verb script
```
- **Table Hierarchy**: Verbs live in script objects within database tables
- **JITC**: Scripts use Just In Time Compilation ("jit-see") by the runtime
- **Kernel Integration**: Scripts call C kernel implementations for core functionality
- **Hybrid Model**: Many verbs are UserTalk scripts that call other verbs

#### **2. Verb Syntax**
```
verb (param1, param2)           // Standard call with parameters
verb ()                          // Call with no parameters
verb (param2: val2)             // Named parameter override
adrVerb^ ()                     // Dereferenced address call
```
- **Table Context**: `category` is actually a table in the database
- **Global Scope**: Top-level tables in databases are in global scope
- **Parameters**: Parentheses-enclosed parameter lists with optional defaults
- **Named Parameters**: Can override specific parameters by name using `param: value` syntax

#### **3. Database Integration**
- **Address References**: Objects referenced as `@table.subtable.object`
- **Address Type**: `addressType` is a native UserTalk type for object addresses
- **Dereferencing**: Use `^` operator to access addressed objects (works for any object type)
- **Path-Based Access**: Uses path strings to navigate database hierarchy
- **Live Updates**: Changes to database objects are immediately reflected in UI

## Core Language Structures

### **1. Repetition (Looping)**

#### **`for` Loops**
```usertalk
// Counter-based iteration
for i = 1 to 5
    msg (i)
    clock.waitSeconds (1)

// List iteration
for element in finderMenu.getSelectionList ()
    dialog.alert (element)
```

#### **`while` Loops**
```usertalk
while not file.endOfFile (f)
    msg (file.readLine (f))
```

#### **`fileloop` Structure**
```usertalk
// Basic file iteration
fileloop (f in path)
    msg (file.fileFromPath (f))

// With depth parameter
fileloop (f in path, infinity) //visit all files at all levels
    msg (file.fileFromPath (f))
```

#### **`loop` Structure**
```usertalk
loop
    msg (i)
    i = i + 1
    if i > 5
        break
```

### **2. Decisions (Branching)**

#### **`if/else` Structure**
```usertalk
if answer > 6
    msg ("Big family!")
else
    msg ("Not such a big family!")
```

#### **`case` Structure**
```usertalk
case letter
    "a"
    "e"
        msg ("Vowel")
    "b"
        msg ("Consonant")
    else
        msg ("This example isn't very thorough.")

// Equivalent to else-if
case true
    temperature < minimum
        dialog.alert ("Too cold.")
    temperature > maximum
        dialog.alert ("Too hot.")
    else
        dialog.notify ("Delicious porridge.")
```

### **3. Error Handling**

#### **Prevention Strategy**
```usertalk
if file.exists (f)
    file.delete (f)
```

#### **Status Checking**
```usertalk
if file.open (f)
    theLine = file.readLine (f)
```

#### **`try/else` Structure**
```usertalk
try
    file.delete (f)
else
    dialog.alert (tryError)
```

### **4. Code Organization**

#### **`bundle` Structure**
```usertalk
bundle //create a SimpleText file
    file.new (path)
    file.setType (path, "TEXT")
    file.setCreator (path, "ttxt")
```

## Variables and Scope

// Declaration

    x = 3

### **Global Variables**
- **Persistent Storage**: Stored permanently in Frontier Object Database
- **Cross-Session**: Retain values even after script finishes
- **Independent**: Separate from scripts that use them
- **Editable**: Can be viewed and edited independently

## Frontier Verbs (Functions)

UserTalk has hundreds of verbs organized into 21 categories:

### **Key Categories:**

#### **Core Language**
- **`basic`**: Handle numbers, datatypes, objects, etc.
- **`clock`**: Set and get system clock values, pause execution
- **`date`**: Get and set date values

#### **User Interface**
- **`dialog`**: Display and return results from dialog boxes
- **`window`**: Manage and manipulate Frontier windows

#### **System Operations**
- **`file`**: All file operations, including copy, delete, move, create, rename

- **`launch`**: Open applications, control panels, documents
- **`system`**: Deal with external applications and OS information

#### **Database Operations**
- **`table`**: Manipulate and interact with Frontier Object Database tables
- **`db`**: Database operations (most relevant for refactoring)
- **`op`**: Edit, navigate in, rearrange, expand, collapse outline objects

#### **Application Control**
- **`Frontier`**: Turn agents on and off, make Frontier active
- **`target`**: Determine the Frontier object that will receive actions
- **`wp`**: Handle word processing objects and their contents

#### **Advanced Features**
- **`search`**: Handle Frontier's internal find-and-replace operations
- **`speaker`**: Define and activate internal speaker sounds
- **`kb`**: Determine if modifier keys are down
- **`mouse`**: Find mouse position and button state

## Operators and Special Characters

### **Standard Operators**

#### **Assignment**
- `=` - Assignment

#### **Arithmetic**
- `+` - Add numeric values or concatenate strings
- `-` - Subtract numeric values or remove string occurrence
- `*` - Multiplication
- `/` - Division (integer or real)
- `%` - Modulus (remainder of integer division)

#### **Comparison**
- `==` or `equals` - Test for equality
- `!=` or `notEquals` - Test for inequality
- `<` or `lessThan` - Less-than comparison
- `<=` - Less-than-or-equal comparison
- `>` or `greaterThan` - Greater-than comparison
- `>=` - Greater-than-or-equal comparison

#### **String Operators**
- `beginsWith` - Compare one string to the beginning of another
- `contains` - True if one string contains another
- `endsWith` - Compare one string to the end of another

#### **Logical**
- `||` or `or` - Logical OR
- `&&` or `and` - Logical AND
- `!` or `not` - Logical NOT

#### **Increment/Decrement**
- `++` - Increment
- `--` - Decrement

#### **Address Operations**
- `@` - Address-of
- `^` - Dereference an address

### **Special Characters**

#### **String and Character Literals**
- `"abcdef"` - Define a string (with straight quotes)
- `'a'` - Define a character with single quotes
- `'abcd'` - Define a "string4" (exactly four characters)

#### **Object References**
- `[...]` - Evaluate a variable or expression, also used for lists, records
- `["..."]` - Include an object database name that contains spaces

#### **Escape Characters**
- `\` - Treat the next character as a literal
- `\t` - Tab character (in a quoted string)
- `\r` - Return (cr) character (in a quoted string)
- `\n` - Linefeed (lf) or "newline" character (in a quoted string)

## Database Integration Patterns

### **1. Address-Based Navigation**
```
@table.subtable.object    // Address reference
local (adrCreateMessage = @manilaSuite.discuss.createMessage)
adrCreateMessage^ (param1, param2)  // Dereference and call
local (adrTable = @someTable)       // Address to table
adrTable^                            // Dereference table
```

### **2. Object Reference Syntax**
```
path.to.parentOfMyObject.["My Object"]  // Object with special characters
tableName.objectName                     // Standard object reference
parentTable.["Object With Spaces"]       // Object with spaces in name
local (myObjectName = "Object Name"); tableName.[myObjectName]  // Dynamic reference
```

### **3. Path-Based Navigation**
```
"examples.age"           // Direct object access
"examples.[\"key\"]"     // Table key access
"examples[1]"            // Array index access
```

### **4. Database Lifecycle**
```
db.new (filepath)        // 1. Create database
db.open (filepath, false) // 2. Open for access
db.setValue (filepath, "path", value) // 3. Modify data
db.save (filepath)       // 4. Save changes
db.close (filepath)      // 5. Close database
```

### **5. Cross-Database References**
```
["~/Frontier/Guest Databases/apps/Manila.root/"].manilaSuite.discuss.createMessage
```
- **Full Paths**: Can reference objects across different .root files
- **Global Scope**: Top-level tables in all databases are globally accessible
- **Address Resolution**: Runtime resolves addresses across database boundaries

## Address System and Stack Management

### **Address Type System**
- **`addressType`**: Native UserTalk type for object addresses
- **Universal Addressing**: Can assign address of any object (scalars, tables, scripts)
- **Dereferencing**: `^` operator works on any object type, not just scripts
- **Handle Pattern**: Pass address of addressType object to verbs for indirect access

### **Stack Frame Management**
- **Call Stack**: Each script execution creates stack frames
- **In-Memory Storage**: Stack frames stored in temporary in-memory table
- **Stack Walking**: Code can traverse stack table to examine parent frames
- **Frame Objects**: Can access objects and variables in parent stack frames
- **Stack Addresses**: Addresses can reference objects in stack frames

### **Address Scope**
- **Database Objects**: Addresses to persisted .root file objects
- **Stack Objects**: Addresses to objects in current stack frame
- **Stack References**: Addresses to objects in parent stack frames
- **Dynamic Scope**: Addresses can reference temporary stack-based objects

## Type System and Naming Conventions

### **Dynamic Type System**
- **No Pre-declaration**: Variables have no type until assigned
- **Runtime Conversion**: Automatic type conversion based on context
- **Operator Context**: `50 + "1"` returns `"501"` (string concatenation)
- **Type Inference**: Runtime determines intended operation from operand types

### **Data Types**
- **Scalar Types**: Numbers, strings
- **Complex Types**: Arrays, records (maps), tables
- **Mixed Content**: Tables can contain any type of object
- **Named Objects**: All table objects must have unique names

### **Naming Conventions**
- **Case-Insensitive**: `myVariable` and `myvariable` refer to same object
- **Table Object Names**: Can be any string (including spaces and special characters)
- **Special Character Access**: Use `tableName.["Object Name"]` for objects with special characters
- **Dynamic References**: Use `tableName.[variableName]` for dynamic object access
- **Script Variable Names**: Must start with letter, can contain letters/numbers/underscore
- **UserLand Style**: Typically camelCase, occasionally all lowercase, rarely underscores
- **Unique Names**: All names in a table must be unique

### **Dynamic Object Operations**
- **Dynamic References**: `local (myObjectName = "Object Name"); tableName.[myObjectName]`
- **Name Retrieval**: `nameOf (adrObject)` - Get name of object at address
- **Address Variables**: Use `addressType` variables for dynamic object manipulation
- **Runtime Resolution**: Object names resolved at runtime for dynamic references

## Implicit Returns and Memory Management

### **Implicit Return Behavior**
UserTalk has implicit return behavior where the last expression in a script block is automatically returned:

#### **Basic Implicit Returns**
```usertalk
on myHandler()
    local(x, y)
    x = 5
    y = 10
    x + y  // This is implicitly returned
```

#### **Common Pattern in Web Templating**
```usertalk
htmltext = htmltext + s  // Implicitly returns updated htmltext
```

### **Memory Management Optimization**
A significant optimization quirk for production systems:

#### **The Problem**
```usertalk
htmltext = htmltext + s  // Allocates memory for implicit return
return(something)         // Implicit return memory is immediately dropped
```

#### **The Solution**
```usertalk
htmltext = htmltext + s;  // Semicolon prevents implicit return allocation
return(something)          // No wasted memory allocation
```

## Data Structures and Collections

### **Arrays and Records**
Both arrays and records in UserTalk are heterogeneous collections that can contain elements of any type:

#### **Arrays**
- **Syntax**: `{item1, item2, item3}`
- **Heterogeneous**: Can contain strings, numbers, booleans, tables, scripts, outlines, etc.
- **Indexed Access**: Zero-based indexing
- **Dynamic**: Size can change at runtime

#### **Records**
- **Syntax**: `[key1: value1, key2: value2]`
- **Key-Value Pairs**: Associative data structure
- **Heterogeneous**: Values can be any UserTalk type
- **String Keys**: Keys are typically strings but can be other types

### **Complex Object Storage**
Both arrays and records can store complex UserTalk objects:
- **Tables**: `{table1, table2, table3}`
- **Scripts**: `[handler: on myHandler() { return(42) }]`
- **Outlines**: `{outline1, outline2}`
- **Mixed Types**: `{42, "string", true, myTable, on handler() { return(x) }}`

## Script Editor and Outline View

### **Outline View Behavior**
The Frontier script editor uses an outline view similar to code editors with "folding" features:

#### **Visual Representation**
- **Indentation-Based**: Uses indentation to represent code block structure
- **Hidden Syntax**: Curly braces `{}` are hidden in the UI
- **Folding**: Sub-blocks can be collapsed/expanded
- **Clean Interface**: Focuses on logical structure over syntax

#### **Local Variable Declaration**
The outline view has special handling for `local()` declarations:

```
local
    x
    y = 42
    z = "hello"
```

**UI Behavior**:
- **Hidden Parens**: `local()` parentheses are hidden
- **Hidden Commas**: Commas between variables are hidden
- **Indented Variables**: Each variable appears as an indented heading
- **Optional Assignment**: Variables can have optional initial values

#### **String Conversion**
When converting between outline view and string representation:

**Outline → String**:
- Adds hidden curly braces `{}`
- Adds hidden parentheses `()`
- Adds hidden commas `,`
- Preserves indentation with tab characters

**String → Outline**:
- Removes visible curly braces `{}`
- Removes visible parentheses `()`
- Removes visible commas `,`
- Converts indentation to outline structure

### **Implementation Location**
The script editor's outline view functionality is likely implemented in:
- **UI Code**: Script editor interface components
- **Conversion Logic**: String ↔ outline view conversion
- **Display Logic**: Rendering outline structure
- **Editing Logic**: Handling outline-based editing

## Outline System and UI Integration

### **Outline as Universal UI Pattern**
Outlines are a fundamental UI pattern throughout Frontier, not just for scripts:

#### **Table Windows as Outlines**
- **Expandable/Collapsible**: Sub-tables can be expanded/collapsed like outline headings
- **Hierarchical Structure**: Tables can contain nested sub-tables
- **Consistent UI**: Same outline interface used for tables and scripts
- **Visual Navigation**: Tree-like structure for data exploration

#### **Outline Heading Properties**
Each outline heading has several key properties:

##### **Refcon (Reference Container)**
- **Binary Blob**: Optional binary data attached to heading
- **Additional Properties**: May store heading-specific metadata
- **Flexible Storage**: Can contain any binary data
- **Script Objects**: May or may not use refcons (implementation unknown)

##### **isComment Property**
- **Boolean Flag**: `isComment = true` marks heading as comment
- **Compilation Behavior**: Comment headings are not compiled/interpreted
- **String Conversion**: Comments preceded with `//` in string form
- **UI Indication**: Chevron `«` icon instead of triangle for comments

### **Script Editor Comment Handling**

#### **Comment Detection**
```
// This is a comment heading
local(x)
    x = 42
    return(x)
```

**UI Behavior**:
- **Visual Indicator**: Chevron `«` icon for comment headings
- **Non-Compiled**: Comment headings skipped during execution
- **String Format**: Comments automatically prefixed with `//`
- **Outline View**: Comments appear as collapsed by default

#### **String Conversion for Comments**
**Outline → String**:
- Comment headings: `// Comment text`
- Regular headings: `headingName`
- Preserves indentation and structure

**String → Outline**:
- Lines starting with `//`: Convert to comment headings
- Sets `isComment = true` for comment headings
- Maintains outline structure

## XML Integration and Table Structure

### **xml.decompile Verb Behavior**
The `xml.decompile` verb creates a unique table structure to handle XML document representation:

#### **Table Structure with Numbered Prefixes**
When decompiling XML, each sub-element name is prefixed with:
- **3-digit number**: Preserves element order
- **Tab character**: Separates number from actual element name
- **Hidden in UI**: Number and tab are hidden unless editing object name

#### **Example XML Decompile Result**
```xml
<root>
  <item>value1</item>
  <item>value2</item>
  <section>
    <item>value3</item>
  </section>
</root>
```

**Table Structure Created**:
```
root
├── 001	item = "value1"
├── 002	item = "value2"  
├── 003	section
    └── 001	item = "value3"
```

**UI Behavior**:
- **Normal View**: Shows `item`, `item`, `section` (prefixes hidden)
- **Edit Mode**: Shows `001	item`, `002	item`, `003	section` (prefixes visible)
- **Order Preservation**: Numbers ensure correct element order
- **Duplicate Names**: Multiple elements with same name handled correctly

### **Implementation Purpose**
This quirky hack solves several XML representation challenges:

#### **Problem Solved**
- **Element Order**: XML elements have specific order that must be preserved
- **Duplicate Names**: Multiple elements with same name at same level
- **Hierarchical Structure**: Nested elements must maintain relationships
- **Table Limitations**: Standard tables don't preserve order or handle duplicates

#### **Solution Benefits**
- **Order Preservation**: 3-digit numbers maintain element sequence
- **Duplicate Handling**: Multiple `item` elements distinguished by numbers
- **UI Clarity**: Normal browsing hides technical prefixes
- **Edit Capability**: Full names visible when editing
- **Backward Compatibility**: Works with existing table operations

## Epynomous Handlers (Verb Definitions)

### **Handler Syntax Patterns**
```
on verb ()                    // Takes no parameters
on verb (p1, p2)             // Takes two required parameters
on verb (p1=100, p2=0)       // Takes two optional parameters with defaults
```

### **Parameter Override Syntax**
```
verb (p2: 5)                 // Override default value for p2
verb (param1, param2: val2)  // Mix positional and named parameters
```

### **Handler Implementation**
- **Epynomous Handlers**: Define verb behavior using `on verb()` syntax
- **Default Values**: Parameters can have default values in handler definition
- **Named Overrides**: Callers can override specific parameters by name
- **Flexible Syntax**: Supports various parameter patterns and combinations

## Database Verbs (Most Relevant for Refactoring)

### **Core Database Operations**

#### **`db.new (f)`**
- **Purpose**: Create a new, empty .root database file
- **Parameters**: `f` - filespec or path string for new database
- **Returns**: `true` on success
- **Notes**: Creates minimal database with no UI support objects

#### **`db.open (f, readOnly)`**
- **Purpose**: Open an existing .root database file
- **Parameters**: 
  - `f` - filespec or path string of database file
  - `readOnly` - boolean for read-only vs read-write access
- **Returns**: `true` on success
- **Notes**: Must be called before other db verbs (except `db.get` and `db.set`)

#### **`db.close (f)`**
- **Purpose**: Close an opened database file
- **Parameters**: `f` - filespec of opened database
- **Returns**: `true` on success
- **Notes**: Does not save changes - `db.save` must be called separately

#### **`db.save (f)`**
- **Purpose**: Save changes to database file
- **Parameters**: `f` - filespec of opened database
- **Returns**: `true` on success
- **Notes**: Required to persist changes made with write verbs

### **Data Access Verbs**

#### **`db.getValue (f, path)`**
- **Purpose**: Get value of object in opened database
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to object
- **Returns**: Value of specified object

#### **`db.setValue (f, path, value)`**
- **Purpose**: Set value of object in opened database
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to object
  - `value` - new value to set
- **Returns**: `true` on success

#### **`db.defined (f, path)`**
- **Purpose**: Check if object exists in database
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to object
- **Returns**: `true` if object exists, `false` otherwise

### **Table Operations**

#### **`db.isTable (f, path)`**
- **Purpose**: Check if object is a table
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to object
- **Returns**: `true` if object is a table

#### **`db.newTable (f, path)`**
- **Purpose**: Create new table in database
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string for new table
- **Returns**: `true` on success

#### **`db.countItems (f, path)`**
- **Purpose**: Count items in table
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to table
- **Returns**: Number of items in table

#### **`db.getNthItem (f, path, n)`**
- **Purpose**: Get nth item in table
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to table
  - `n` - index of item (1-based)
- **Returns**: Value of nth item

### **Object Management**

#### **`db.delete (f, path)`**
- **Purpose**: Delete object from database
- **Parameters**: 
  - `f` - filespec of opened database
  - `path` - path string to object
- **Returns**: `true` on success

#### **`new (type, addr)`**
- **Purpose**: Create new object of specified type at address
- **Parameters**: 
  - `type` - valid Frontier datatype (e.g., `tableType`, `outlineType`, `booleanType`)
  - `addr` - location in Frontier Object Database table
- **Returns**: `true` on success, `false` otherwise
- **Examples**: 
  - `new (tableType, @topLevelTable.myTable)`
  - `new (outlineType, @examples.newOutline)`

## Additional details from newly added docs

### Control structures and declarations
- **with blocks**: Supported structure for operating within a temporary context. See grammar reference for exact semantics. Example skeleton:
```usertalk
  with targetObject
      // statements
```
- **global declarations**: Declare persistent variables explicitly using either outline or inline form:
```usertalk
  global
      x
      y = 1
  // or
  global (x, y = 1)
  ```
- **loop control**: Both `break` and `break()` forms exist; `continue` is also available to skip to the next iteration.

### Quick Script window syntax
- Multi-line scripts in Quick Script require punctuation to express structure:
  - Use `;` where a new line would appear in a script outline
  - Use `{ ... }` to represent indented blocks

Example:

```usertalk
// Outline/script editor form
if answer >= 6
    msg ("Big family!")
else
    msg ("Not such a big family!")
```

Quick Script equivalent:

```usertalk
if (answer >= 6) { msg ("Big family!") } else { msg ("Not such a big family!") }
```

### Concurrency and background processing
- Frontier’s runtime is multi-threaded:
  - `thread` verbs: launch and coordinate concurrent scripts
  - `semaphore` verbs: coordinate shared resource access
  - Agent scripts and scheduled scripts: periodic/background execution
  - Responders architecture: request-driven execution (e.g., web server)

### Interoperability (platform integration)
- macOS: Apple Events integration; UserTalk can respond to incoming events
- Windows: COM server interface can invoke UserTalk scripts
